# MyStore “Super Web” Modernization Plan

## Goal

Transform the entire MyStore ecosystem into a cohesive, modern professional business platform across admin, executive, POS, storefront/customer, delivery, warehouse, HR, finance, support, and partner experiences, while redesigning the data foundation for correctness, tenant safety, analytics quality, scalability, accessibility, and maintainability.

This will be delivered as an incremental migration, not a big-bang rewrite. Every phase must keep the platform buildable and the canonical FastAPI backend compatible with both monolith and microservice deployment modes.

## Current-state findings that shape the work

- The canonical frontend is React 19/Vite with 10 lazy-loaded experience apps and roughly 30 admin routes (`apps/web/src/App.tsx`, `apps/web/src/apps/admin/AdminApp.tsx`).
- The admin UI has reusable Radix/Tailwind primitives, but role-specific shells independently hardcode colors, layout, auth, and navigation (`apps/web/components/enterprise-shell.tsx`, `apps/web/src/apps/ceo/ExecutiveShell.tsx`, `apps/web/src/apps/pos/PosLayout.tsx`, and the storefront page).
- Dashboard trends include hardcoded comparison values and derive totals from limited list responses, so they are not decision-grade (`apps/web/app/dashboard/page.tsx`). The reporting API loads broad datasets into Python and aggregates in memory (`services/backend-py/app/modules/reporting/api.py`).
- The shared table is client-paginated only, while several endpoints ignore or incompletely calculate server pagination (`apps/web/components/data-table/data-table.tsx`, `services/backend-py/app/modules/catalog/api.py`).
- Public storefront code calls the authenticated products endpoint with a fake `guest` token instead of the existing public endpoint, and the backend public endpoint is not explicitly tenant/store scoped (`apps/web/app/shop/page.tsx`, `services/backend-py/app/modules/catalog/api.py`).
- Auth tokens are persisted in localStorage; user roles exist both as a JSON string and in relational role tables (`apps/web/lib/auth-store.ts`, `services/backend-py/app/modules/identity/models.py`).
- Alembic exists, but the current “baseline” is autogenerated against an existing schema and alters/drops many existing objects rather than creating a clean schema. CI currently uses `create_all`, not migration upgrade, which hides migration defects (`services/backend-py/alembic/versions/211a671f4cb5_baseline_schema.py`, `services/backend-py/tests/conftest.py`, `.github/workflows/ci.yml`).
- Frontend checks stop at TypeScript compilation; there are no Vitest or Playwright tests (`apps/web/package.json`, `.github/workflows/ci.yml`).

## Delivery strategy

### Phase 0 — Safety baseline and measurable acceptance criteria

1. Capture current build, typecheck, backend test, and schema-audit results before changing behavior.
2. Add an application inventory and route/endpoint coverage matrix for all experiences.
3. Define platform-wide quality targets: WCAG 2.2 AA, responsive breakpoints, keyboard operation, loading/error/empty states, core Web Vitals budgets, API latency budgets, tenant-isolation tests, and migration-from-empty verification.
4. Add frontend test infrastructure with Vitest, Testing Library, axe checks, and Playwright smoke journeys.
5. Extend CI to build the web app, run frontend tests, and create the database using `alembic upgrade head` before running backend integration tests and the schema audit.

### Phase 1 — Unified professional design system and application frame

1. Introduce semantic design tokens for color, typography, spacing, density, elevation, motion, data visualization, status, and focus states in `apps/web/app/globals.css`; preserve light, dark, system, and reduced-motion behavior.
2. Standardize primitives and patterns: buttons, fields, selects, validation, cards, metric cards, tables, filters, page headers, tabs, drawers, dialogs, confirmation flows, toasts, banners, skeletons, empty/error states, charts, and responsive overflow.
3. Replace hardcoded slate/zinc/indigo shells with shared persona-aware shell components. Keep workflows tailored by role, but share brand, theme, accessibility, responsive navigation, notifications, user menu, and connection/data-freshness indicators.
4. Replace the development-only DomainBar in production with permission-aware app/workspace switching backed by `/apps/my-apps` and `/apps/check-access`.
5. Create centralized route metadata for labels, icons, permissions, section grouping, breadcrumbs, default routes, and command-palette entries; remove duplicate navigation definitions.
6. Add accessible skip links, semantic landmarks, visible focus, screen-reader labels, mobile navigation behavior, and keyboard shortcuts that do not conflict with browser/assistive technology.

### Phase 2 — Decision-grade business command center

1. Replace client-derived dashboard totals and hardcoded percentage changes with a versioned dashboard API that returns current period, comparison period, currency, timezone, freshness timestamp, and definitions for every KPI.
2. Build role-aware dashboards for executive, store manager, finance, HR, warehouse, delivery, support, and partner personas using a shared dashboard composition system.
3. Add actionable insight cards rather than decorative metrics: low-stock replenishment, overdue approvals, failed payments, late deliveries, unresolved SLA breaches, cash reconciliation variance, payroll exceptions, and margin erosion.
4. Upgrade reporting to real charts with accessible tabular equivalents, date/branch/channel filters in the URL, drill-down links, export jobs, loading/error recovery, and clear “no data” explanations.
5. Use organization currency/timezone settings everywhere through shared formatters; remove hardcoded USD and locale assumptions.

### Phase 3 — Data model and migration redesign

1. Replace the unsafe autogenerated baseline with a reviewed, reproducible migration chain that can create an empty PostgreSQL database and upgrade existing installations safely. Back up and validate before any live migration.
2. Complete relational identity and authorization: make `user_roles` authoritative, add role-permission relationships and scoped assignments, backfill from `users.roles`, dual-read during migration, then remove the JSON role column in a later compatible migration.
3. Introduce explicit tenant/store resolution for public commerce (hostname/store slug or signed storefront identifier). Every public product/order query must scope to one active organization/store; never expose cross-tenant catalog data.
4. Add durable business-data constraints and indexes: tenant-scoped uniqueness for SKU/barcode and business identifiers, composite indexes matching filters, foreign keys for currently unbound references, non-negative monetary/quantity checks where appropriate, normalized currency codes, and timezone-aware timestamps.
5. Establish audit fields and soft-delete/archive policy for mutable master data. Ensure security-sensitive and financial state transitions append audit events.
6. Add an analytics read model: SQL views/materialized summaries or aggregate tables for daily sales, margins, channel/branch performance, inventory health, and operational alerts. Update them transactionally or through the existing outbox/event pipeline.
7. Move report aggregation from broad Python in-memory scans to filtered SQL/grouped queries or read models. Add comparison periods and stable KPI definitions.
8. Add data-quality jobs and APIs for duplicates, orphan references, missing classifications, negative stock anomalies, stale inventory counts, unbalanced journals, and invalid contact information.
9. Make pool sizing and timeouts configurable, add statement timeouts, and plan PgBouncer/read-replica compatibility without prematurely splitting the shared database.

### Phase 4 — Core business workflow modernization

Migrate each area onto the new system in vertical slices, with API/contract/UI/tests completed together:

1. Catalog and inventory: server pagination/search/filter/sort, category/brand support, image/media model, variant editing, bulk import/export, stock-by-location, valuation, replenishment actions, barcode workflows, and audit history.
2. Sales and POS: fast keyboard/barcode operation, durable offline queue, shift/drawer lifecycle, quotes/returns/refunds, server-priced promotions/tax, split tender, receipt/invoice output, and reconciliation.
3. CRM and loyalty: customer timeline, segmentation, addresses/contacts, consent, credit terms, loyalty/store-credit history, deduplication, and privacy controls.
4. Procurement/WMS/delivery: supplier lifecycle, purchase approvals, receiving and three-way matching, transfers, pick-pack-ship, route/driver assignment, proof of delivery, COD reconciliation, and exception queues.
5. Finance/assets: period controls, journals, trial balance, statements, receivables/payables, tax reporting, asset depreciation, immutable posting rules, and export/audit evidence.
6. HR/projects/support: people directory, leave/payroll approvals, timesheets/project profitability, ticket SLA queues, ownership, comments, and resolution workflows.
7. Platform/admin/partner: tenant provisioning, app access, RBAC editor, audit explorer, notification preferences, API keys/webhooks, automation runs, secret handling, and operational status.

### Phase 5 — Storefront and customer experience

1. Create a dedicated public API client that calls `/public/*` endpoints without forged authentication.
2. Redesign storefront navigation, real category filters, search, product details/variants/media, stock availability, persistent cart, checkout validation, order confirmation, and tracking.
3. Move price, discount, tax, stock, and final totals entirely to the server; the browser sends variant and quantity, never authoritative unit price.
4. Add authenticated customer account flows, address book, order history, invoice access, shipment timeline, loyalty balance, and returns/support entry points.
5. Add storefront SEO metadata/rendering strategy, performance budgets, optimized media, and analytics/consent boundaries.

### Phase 6 — Reliability, security, observability, and release quality

1. Migrate browser authentication toward secure HttpOnly, SameSite cookies with refresh rotation and CSRF protection; keep a transitional bearer-token adapter for non-browser clients.
2. Move distributed rate limiting/session revocation to Redis and enforce permission dependencies server-side for every sensitive endpoint.
3. Add structured logs, request/trace correlation, OpenTelemetry export, real metrics rather than static values, health/readiness checks, alert thresholds, and audit dashboards.
4. Add contract tests, tenant-isolation tests, permission-matrix tests, migration tests, API integration tests, accessibility tests, visual-regression tests, and Playwright journeys for each persona.
5. Add performance checks for representative datasets, query plans for reporting/list endpoints, bundle budgets, error monitoring, backup/restore rehearsal, and staged rollout/rollback procedures.

## Implementation sequencing inside each phase

For each vertical slice:

1. Define or update shared contracts in `packages/contracts`.
2. Add a reviewed Alembic migration and backfill where required.
3. Implement tenant-scoped backend behavior and permission enforcement in `services/backend-py`.
4. Add unit and PostgreSQL integration tests, including cross-tenant negative cases.
5. Implement the shared frontend components and the persona-specific workflow in `apps/web`.
6. Add component/accessibility tests and a Playwright happy path plus one failure path.
7. Run typecheck, web build, frontend tests, backend tests, migration-from-empty, upgrade rehearsal, and schema audit.
8. Update architecture documentation only after verification reflects the actual implementation.

## First implementation milestone after approval

Start with the foundation and one complete, visible vertical slice:

- CI/frontend test setup and migration-from-empty gate.
- New semantic design tokens and shared application shell/navigation metadata.
- Server-backed dashboard summary with real comparison periods, freshness, currency/timezone, and actionable alerts.
- Modern professional executive/admin dashboard using the new components.
- Reporting query optimization and tests.
- Initial relational-RBAC compatibility migration (backfill and dual-read, not destructive removal).
- Public catalog endpoint correction for explicit storefront tenant scope, with cross-tenant tests.

This milestone proves the architecture, design language, database migration process, and quality gates before rolling the same patterns through all remaining experiences.

## Verification and acceptance

A phase is complete only when:

- The application builds and typechecks.
- All backend, frontend, accessibility, and relevant end-to-end tests pass.
- A clean database reaches `alembic head`; an upgrade copy of the current schema also reaches head without data loss.
- Tenant isolation and permission denial cases are tested.
- Dashboard/report values reconcile against database fixtures and documented formulas.
- Main journeys work at mobile, tablet, and desktop widths with keyboard navigation.
- No experience relies on hardcoded demo KPIs, forged guest tokens, client-authoritative prices, or unscoped public data.
- Documentation and screenshots reflect the verified implementation, not aspirational status.
