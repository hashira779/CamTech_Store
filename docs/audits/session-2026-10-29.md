## Fixed in this session

### 1. CRITICAL — checkout trusted the client's price (zero-trust #45)
`CheckoutOrchestrator.calculate_totals_and_lines` used `items[].price` from the request body as the unit price.
Anyone could POST `price: 0.01` to `/sales/store-checkout` and get a valid ABA/Bakong QR for one cent, which on payment
would finalize the order, deduct stock and dispatch delivery.
**Fix:** the catalog `sellPrice` is now the floor: `unit = max(client_price, catalog_price)`. A higher client price is
still accepted because the Mini App's size/add-on options (`SIZE_OPTIONS`, `ADD_ONS` in `apps/mini/src/App.tsx`) are not
modelled in the catalog yet — see open item O4.

### 2. HIGH — cart lines silently mapped to random / other-tenant products
Unknown item ids fell back to "first variant in the org", then "first variant in **any** org"; id/SKU lookups were not
scoped to the store. Result: wrong product on the invoice and stock deducted from an unrelated item.
**Fix:** `_resolve_variant` only matches **active variants of the target store** (variant id → product id → SKU).
Anything else → `400 "'<name>' is not available in this store."` Quantity ≤ 0 → `400`.

### 3. HIGH — cross-tenant fallbacks for org and sale owner
- `resolve_target_org` fell back to the oldest organization when no store could be determined → now `400`.
- `resolve_sale_user` matched the customer email against users of **all** orgs, then fell back to any user anywhere →
  now scoped to the target store; if the store has no staff user → `409`.

### 4. HIGH — double finalize on payment (double stock deduction + duplicate deliveries)
`payment-status` polling, `confirm-payment` and `payway-webhook` all called `_finalize_paid_sale` after a slow bank
round-trip, with only a stale in-memory `status` check. Concurrent calls each deducted stock and created a delivery.
**Fix:** `_finalize_paid_sale` first claims the sale with a conditional
`UPDATE sales SET status='COMPLETED' WHERE id=? AND status<>'COMPLETED'`; only the caller that flips the row continues.

### 5. MEDIUM — webhook could finalize without bank verification
`payway_webhook` skipped verification entirely when no merchant credentials resolved. Now it always requires a positive
`PaywayService.verify_transaction` result.

### 6. MEDIUM — online checkout was not idempotent
POS `/sales` honoured `Idempotency-Key`; `/sales/store-checkout` did not, so a double-tap or network retry created two
orders (and two bank QR codes, two stock deductions for COD).
**Fix:** checkout reads the `Idempotency-Key` header, stores it on `sales.idempotencyKey` and returns the original order
for a repeated key (scoped to the store). A concurrent duplicate that loses the unique-constraint race gets the winner's
order back instead of a 500. A replay returns `qrString`/deeplink but not the rendered QR image.
Frontends do not send the header yet — see O9.

### 9. KHQR payment integration & key vault (enterprise spec)

**Bugs found in the old KHQR path (all fixed):**
- **Wrong payee:** `KhqrGenerator` put the literal `bakong@dev` in tag 29/00 (the account banking apps pay) and the
  store's account in 29/01. Every Bakong QR asked customers to pay `bakong@dev`.
- **MD5 collisions → false "paid":** no timestamp/bill number in the payload, so two orders with the same amount had the
  *same* QR string and MD5; once order A was paid, `check_transaction_by_md5` reported order B paid too.
- **Currency mismatch:** the QR used the store's Bakong *account* currency with the sale's USD total — a $5.00 order
  became a 5-riel QR on a KHR account. QRs are now always in the sale's currency (no exchange-rate source exists).
- **Fake deeplink:** `https://link.payway.com.kh/khqr?amount=…` was invented; removed (deeplink is `null`).

**Delivered:**
- **Zero-API generation:** `domain/commerce_engines.KhqrGenerator.generate_dynamic_qr` builds EMVCo TLV locally — 00 `01`,
  01 `12`, 29 [00 account, 02 acquiring bank], 52 MCC `5999`, 53 `840`/`116`, 54 amount (KHR integer, USD 2dp), 58 `KH`,
  59 name, 60 city, 62 [01 bill number = sale number], 99 [00 created ms, 01 expiry ms], 63 CRC16-CCITT (0x1021).
  `BakongService.generate_khqr` is now synchronous and makes **no** HTTP call; MD5 of the payload is stored on the
  payment (`reference = MD5:<hash>`) and in sale notes with `qrExpiresAtMs` (15 min).
- **Key vault (`core/key_vault.py`):** envelope encryption — per-secret random DEK (AES-256-GCM) wrapped by the KEK
  (`PAYMENT_KEK`, base64 32 bytes, env/KMS-injected; **no default**, fails closed). Stored per secret:
  `encryptedKey`, `iv`, `authTag`, `wrappedDek`, `dekIv`, `dekAuthTag`. The **organization id is AAD on both layers**:
  an envelope copied to another branch fails authentication. Bakong token + webhook secret
  (`settings.bakong.{token,webhookSecret}Sealed`) and PayWay API key / RSA private key (`payway_configs`) are sealed.
- **Masking:** `GET /organizations/current/{bakong,payway}` return `bk_live_••••••••<last4>` / `pw_live_…` only; sending
  the mask (or blank) back keeps the stored secret.
- **Least privilege:** Bakong/PayWay credential GET/PUT now require `ORG_ADMIN`/`SUPER_ADMIN` (any staff user, incl.
  cashiers, could previously redirect the store's payments).
- **Audit trail:** every credential replacement writes `audit_logs` (`PAYMENT_CREDENTIAL_REPLACED`, actor id/email,
  IP via `X-Real-IP`, branch id, changed field names — never values).
- **Signed webhook:** `POST /sales/bakong-webhook` — `X-Webhook-Timestamp` + `X-Webhook-Signature` =
  hex HMAC-SHA256(store webhook secret, `"<ts>.<raw body>"`), ±300 s replay window, constant-time compare; unknown MD5
  and bad signature both answer 401; amount and `toAccountId` must match; duplicates are idempotent via the atomic claim.
- **Rate-limit-resilient polling:** `payment-status` asks the bank only on the schedule 5 s, 15 s, 45 s, 120 s, then every
  120 s from order creation; earlier polls get `retryAfterSeconds` without a bank call. The slot is claimed by a
  compare-and-swap UPDATE, so concurrent pollers make one call. `confirm-payment` goes through the same path. After
  expiry + 60 s grace: one final check, then the sale is `VOIDED` / payment `FAILED` and polling stops (a late verified
  webhook can still complete it). Bakong verification also checks `toAccountId` and amount.
- **Clients:** Mini App, `/mini` and Store poll with `setTimeout` honouring `retryAfterSeconds` and stop on `expired`
  (previously a fixed 2.5 s interval ≈ 60 bank calls per order). Admin Bakong screen shows masks and a webhook-secret field.
  Contracts: `OrderPaymentStatusDto`, masked fields on `BakongConfigDto`, `webhookSecret` on `UpdateBakongConfigInput`.

**Deploy steps (production):** 1) generate `PAYMENT_KEK` (`python -c "import os,base64;print(base64.b64encode(os.urandom(32)).decode())"`)
and inject it into every backend container via the secret store, never Git; 2) `python services/backend-py/scripts/seal_payment_secrets.py`
(dry run) then `--apply` — idempotent, audits each store; 3) deploy. Until step 2 runs, stores with plaintext secrets are
COD-only (fail closed). Losing the KEK makes every sealed secret unrecoverable: back it up in the KMS.

**Tests:** `tests/test_khqr_vault.py` (KHQR layout/CRC/KHR minor unit/unique MD5/invalid input/tamper; vault round-trip,
cross-org, tamper, no KEK, wrong KEK; webhook signature). End-to-end: `e2e_khqr_vault.py` (in-process ASGI, local DB,
Bakong check API replaced by a call counter so no NBC quota is spent).

### 10. Bakong merchant details & "Update failed" alerts (checked against NBC *Bakong Open API Document* v1.0.2)

**Root cause of "Bakong still doesn't work":** per the spec, `check_bakong_account` succeeds with `"data": null` — it
returns **no owner name**. `BakongService.check_bakong_account` did `body.get("data", {}).get("accountName")`, which
raised on `None`; the broad `except` turned that into "invalid", so **every real Bakong account failed verification and
could never be saved**. Only the `*@test` / `*@mock` bypass worked — and that bypass was also live in production, letting
anyone save a fake account whose QRs pay nobody.

**Fixed:**
- Client follows the spec: success on `responseCode 0` regardless of `data`; failures classified by HTTP status / NBC
  `errorCode` → `TOKEN` (401/403, code 6 → "token invalid or expired, renew it"), `NOT_FOUND` (code 11 / responseCode 1),
  `RATE_LIMITED` (429), `UNREACHABLE` (network/5xx/code 9), `NOT_PAID` (code 1), `FAILED` (code 3).
  `*@test` accounts are accepted only with `BAKONG_ALLOW_TEST_ACCOUNTS=1` (set by `tests/conftest.py`, never in prod).
- **Merchant details from the Bakong app:** the store enters the merchant name (NBC returns none), and for merchant
  accounts the **Merchant ID** and **Acquiring Bank**. KHQR now emits tag 30 `[00 account, 01 merchant ID, 02 bank]`
  for merchants and tag 29 `[00 account]` for individuals — matching the spec sample `29190015gg_hh_1980@amkb`.
- **`toAccountId` is no longer compared** on payment confirmation: the spec's own sample settles to
  `bridge_account@devb`, so the earlier check would have rejected real payments. The MD5 already binds payee, amount and
  bill number; amount and currency are still checked.
- **Saves fail loudly, nothing half-written:** `PUT /organizations/current/bakong` validates → checks the account on NBC →
  builds and decodes a probe KHQR → seals secrets, and only then writes. Any failure returns
  `"Update failed — nothing was saved. <reason>"` (400; 502 unreachable; 429 rate-limited). Field rules: account must be
  `name@bank` (≤32), merchant name required, ≤25 printable ASCII (tag 59), city ≤15 (tag 60), MERCHANT needs merchant ID +
  bank, a Bakong API token must exist (store or platform). PayWay save: merchant ID required/format-checked;
  "Update failed — … ABA PayWay did not accept this Merchant ID / API key (sandbox|production)".
- **Readable validation errors everywhere:** request-validation 400s (monolith and every microservice) now say
  `field: reason; …` with a `details[]` list instead of a Python repr of `exc.errors()`.
- **UI:** Bakong and PayWay settings show a red "Update failed — nothing was saved" banner **and** a toast on every
  failed save (client-side pre-checks mirror the server rules); success toasts on save. Removed the fake
  "NBC Verified Owner" badge — replaced by "Account confirmed on Bakong <date>". Account type / Merchant ID / Acquiring
  Bank fields added; Verify uses the saved token when none is typed.
- **Tests no longer leave the demo store modified:** `test_bakong_config` snapshots and restores the store's settings.

### 11. PERF — every request paid ~2s when Redis was down

- **Symptom:** locally every authenticated endpoint took a flat ~2.2s (login ~3.3s) while `/health` took 3ms — the
  "Python is slow" impression. Cause: the IP-ban check and the global rate limiter each tried Redis per request with a
  1s connect timeout (Windows retries a refused connect for ~1s), then fell back to memory — and paid it again next request.
- **Fix:** process-wide breaker [`app/core/redis_breaker.py`](../../services/backend-py/app/core/redis_breaker.py). After
  one transport failure (connection/timeout only — `WRONGTYPE`/bad JSON don't trip it) every caller skips Redis for
  `REDIS_BREAKER_COOLDOWN` seconds (default 30), then a single caller probes. Wired into `IPBanList`, `RateLimiter`,
  `RealtimeEventBus.publish/get_pubsub` and `PasskeyChallengeStore`. In-memory fallbacks are unchanged.
- **Measured (local monolith, Redis stopped):** products 2.25s → 15ms, sales 2.24s → 16ms, dashboard 2.26s → 34ms,
  login 3.3s → 61ms. One warning logged per outage instead of silent per-request waits. Tests: `tests/test_redis_breaker.py`.
- Also: on Windows, `localhost` adds ~0.2s per new connection (IPv6 `::1` tried first); `127.0.0.1` avoids it.
